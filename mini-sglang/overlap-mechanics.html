Overlap 的底层机制

读 scheduler/scheduler.py 时遇到的几个 PyTorch / CUDA 概念。它们合起来解释了一件事：为什么 GPU 在算第 N 批的时候，CPU 能同时处理第 N-1 批的结果。

inference_mode→DISABLE_OVERLAP→CUDA stream→wait_stream→pin_memory→Event.synchronize

01torch.inference_mode()

一句话PyTorch 自带。告诉它「只推理、不反向传播」，于是不记录计算图，更快、更省内存。

平时每次运算 PyTorch 都会记下「结果是怎么算出来的」，留给 .backward() 求梯度。推理用不到这些。

里面产生的张量之后还能参与训练能不能，会报错

两种写法：装饰器 @torch.inference_mode()（run_forever、tokenize_worker）和 with torch.inference_mode():（launch.py 的 _run_scheduler）。run_forever 被包了两层，属于防御性写法，嵌套没问题。

02DISABLE_OVERLAP_SCHEDULING

一句话环境变量开关 MINISGL_DISABLE_OVERLAP_SCHEDULING=1，默认关闭（即默认开启 overlap）。决定用 normal_loop 还是 overlap_loop。

定义在 env.py:69，env.py 会给每个配置项自动加 MINISGL_ 前缀去读环境变量。用在 scheduler.py:122 的 run_forever。

normal_loop（关掉 overlap）：
CPU: [调度 N][发射 N]·········等·········[处理 N 的结果][调度 N+1]...
GPU:                [====算 N====]                              [====算 N+1====]
                                   ↑ GPU 在这段时间闲着

overlap_loop（默认）：
CPU: [调度 N][发射 N][处理 N-1 的结果][调度 N+1][发射 N+1][处理 N 的结果]...
GPU:                [====算 N====][====算 N+1====]
                                   ↑ GPU 几乎不停

关键区别在最后一行：normal_loop 调用 _process_last_data(ongoing_data)，处理刚算完的这一批；overlap_loop 调用 _process_last_data(last_data)，处理上一轮的，并把这一批 return 给下一轮。留这个开关是为了做消融实验（README:143）和方便调试。思路来自 NanoFlow 论文。

03CUDA stream

一句话GPU 的任务队列。同一条 stream 里严格按顺序执行，不同 stream 之间可以同时跑。

先打破一个直觉：在 Python 里写 y = model(x)，CPU 不会等 GPU 算完，只是把 kernel 丢进队列就立刻返回。GPU 调用是「下单」，不是「执行」。

  • with torch.cuda.stream(s): 这个块里提交的 GPU 任务都进 s。
  • torch.cuda.set_stream(s) 不用 with，直接把当前 stream 永久切成 s。
  • 两条 stream 是同一种东西（都是 torch.cuda.Stream()），区别只在分工。

scheduler stream 为什么要碰 GPU

调度决策本身是纯 CPU 的。但模型的输入必须在显存里，所以「决策之后把结果送进 GPU」的拷贝和小计算都是 GPU 任务，比如 _make_positions 的 .to(device)、page_table[input_mapping]、allocate_paged、attn_backend.prepare_metadata。

为什么不全放进 engine stream

全放一条：
engine stream:    [===== forward N =====][拷贝/查表 N+1][===== forward N+1 =====]
                                          ↑ 要等 forward N 做完才轮到

分两条：
scheduler stream: [拷贝/查表 N+1]                ← 和 forward N 同时进行
engine stream:    [===== forward N =====][===== forward N+1 =====]

为什么 engine 不用默认 stream

CUDA Graph 录制不能在默认 stream 上进行（engine/graph.py:140）。所以 Engine 自建一条，forward_batch 开头还 assert torch.cuda.current_stream() == self.stream，这就是 scheduler 每次都要 with self.engine_stream_ctx: 的原因。

04wait_stream

一句话A.wait_stream(B)：在 A 的队列里插一个依赖，A 后面的任务要等 B「此刻已提交的」任务做完才开始。CPU 不等。
比喻：餐厅后厨 CPU 是服务员，只负责递单子，递完就走。厨师 A（scheduler stream）备菜，厨师 B（engine stream）炒菜，各干各的。不加约束的话，B 可能拿着空盘子就开炒。 wait_stream 就是服务员在 B 的单子前插一张纸条：「等 A 把手头的单子做完再往下做」。插完服务员马上走开去招呼别桌。真正在等的是厨师 B，不是服务员。 
forward_input = self._schedule_next_batch()      # 给厨师 A 递单：拷数据到 GPU
with self.engine_stream_ctx:                      # 接下来的单子给厨师 B
    self.engine.stream.wait_stream(self.stream)   # 在 B 的架子上插纸条
    self._forward(forward_input)                  # 给 B 递单：跑模型
self._process_last_data(last_data)                # 服务员已经走开，处理上一桌

对比 torch.cuda.synchronize()：服务员站在厨房门口等所有菜做完，这才是阻塞 CPU。

待回答如果删掉 wait_stream 那一行，可能会出什么错？用厨师的比喻说一句。

05pin_memory

一句话分配一块「钉死」在物理内存上的 CPU 内存（锁页内存），GPU 的搬运单元可以直接读，所以 CPU→GPU 拷贝能真正异步。

普通内存（pageable）的物理位置操作系统随时可以挪，甚至换到硬盘。GPU 的 DMA 引擎按物理地址读数据，怕读到中途被挪走，所以 CUDA 会先让 CPU 把数据拷到一块锁定的中转区：

普通内存：  普通内存 ──CPU 亲自拷──▶ 锁定中转区 ──DMA──▶ 显存
                     ↑ CPU 被拖住，non_blocking 基本失效

锁页内存：  锁页内存 ──DMA──▶ 显存
           CPU 下完单就走
# scheduler.py  _make_positions
indices_host = torch.empty(n, dtype=torch.int32, pin_memory=True)  # 开一块锁页内存
...                                                                # CPU 上填好位置编号
return indices_host.to(device, non_blocking=True)                  # 异步拷进显存

# prefill.py
device_ids.copy_(input_ids[_slice].pin_memory(), non_blocking=True) # 先复制到锁页内存再拷

两个代价

  • 不能滥用。锁页内存操作系统不能挪也不能换出，锁太多整台机器内存会紧张；分配也比普通内存慢。
  • 拷完之前不能改这块 CPU 数据。CPU 下完单就走，GPU 可能还没读。所以 mini-sglang 每次新开 torch.empty(...) 而不复用；scheduler.py:34 的 ForwardInput 缓存数据「to avoid IMA」（illegal memory access）也是同理：异步时数据要活到 GPU 用完。

06Event.synchronize：CPU 唯一主动等 GPU 的地方

一句话在 stream 里插一个标记，CPU 调用 synchronize() 时停下来，等 GPU 跑到这个标记为止。
# engine/engine.py  forward_batch 结尾
next_tokens_cpu = next_tokens_gpu.to("cpu", non_blocking=True)  # 异步拷回 CPU，也只是下单
copy_done_event = torch.cuda.Event()
copy_done_event.record(self.stream)                             # 在 engine stream 插标记

# scheduler.py  _process_last_data 开头
copy_done.synchronize()                                         # 真正等到 token 拷回来

只等「next token 拷回 CPU」这一件事，而不是等整个 GPU 空闲。在 overlap 模式下，这时 GPU 很可能已经在算下一批了。

∑串起来

CPU 线程:         [准备 N+1 元数据]→[提交 forward N+1]→[sync 等 N 的 token]→[处理 N 的结果]→ ...
                       │                 │
scheduler stream:  [pinned→GPU 拷贝, 查页表 N+1]
                                    ↘ wait_stream
engine stream:     [===== forward N =====][===== forward N+1 =====]
                                     ↑ Event: N 的 token 已拷回 CPU
  • stream 让搬运和计算能在 GPU 上并行。
  • wait_stream 保证计算不会抢在数据就绪之前开始，而且不拖住 CPU。
  • pin_memory 让 CPU→GPU 拷贝真正异步，CPU 下完单就能走。
  • Event.synchronize 让 CPU 只在真正需要结果时才等，而且只等那一个结果。
