API Server 的异步与消息

读 server/api_server.py 的 wait_for_ack 时展开的几个问题：进程之间怎么传消息，一个线程怎么同时服务上千个流式请求，以及 asyncio 在底层是怎么把睡着的请求叫醒的。

ZMQ→收发室模式→Event 为什么先 clear→为什么要 wait→唤醒链→async 基础

01ZMQ：进程之间传消息

一句话ZeroMQ 是一个消息传递库，跑在 CPU 上，让不同进程互相发消息。跟 GPU 无关。

mini-sglang 的几个进程之间内存不共享，所以消息（TokenizeMsg、UserMsg 等）要序列化成字节，经 ZMQ 发过去。地址形如 ipc:///tmp/minisgl_3，表示同一台机器上的进程间通信。用到两种模式：PUSH/PULL（一对一单向）和 PUB/SUB（rank 0 广播给其他 rank）。

和另外两种「通信」的区别

ZMQCUDA streamNCCL
运行在CPUGPUGPU
连接进程 ↔ 进程CPU → 同一块 GPUGPU ↔ GPU
传什么控制消息：文字、token id、uidGPU 任务：kernel、拷贝大张量：模型中间结果
代码位置utils/mp.py、scheduler/io.pyscheduler.py、engine.pydistributed/
比喻：餐厅ZMQ 是前台、后厨、收银台之间传递的单子；CUDA stream 是厨师面前那排待做的单子；NCCL 是几个后厨合做一道大菜时互相传半成品。

和 RabbitMQ 的区别

RabbitMQ:  生产者 ──▶ [ RabbitMQ 服务器 ] ──▶ 消费者     有中间人（broker）
ZeroMQ:    生产者 ─────────────────────▶ 消费者           没有中间人，Zero 指的就是这个
RabbitMQZeroMQ
形态要单独部署的服务器一个库，import zmq
消息存哪broker 里，可持久化只在内存，进程挂了就没了
可靠性确认、重试、死信队列基本没有
延迟多一跳极低，同机 ipc 更快

mini-sglang 选 ZeroMQ：所有进程在同一台机器；每个 token 都要传一次，延迟敏感；某个进程挂了整个服务就挂了，消息不需要持久化；不用额外部署服务。

02收发室模式：wait_for_ack

一句话一个后台协程从 ZMQ 收所有回信，按 uid 分进各自的信箱并按门铃；每个 HTTP 请求只在自己的门铃上睡觉。

问题：detokenizer 发回的消息全挤在一条通道里，[uid=3 "你"] [uid=7 "Hello"] [uid=3 "好"] …，需要按 uid 分拣给各自的请求。

比喻：公寓收发室 listen() 是唯一的邮递员；ack_map[uid] 是每户的信箱（list）；event_map[uid] 是每户的门铃（asyncio.Event）；wait_for_ack(uid) 是在家等信的住户。
# new_user()：入住，开信箱、装门铃
self.ack_map[uid] = []
self.event_map[uid] = asyncio.Event()

# listen()：邮递员
msg = await self.recv_tokenizer.get()
self.ack_map[msg.uid].append(msg)      # 放进信箱
self.event_map[msg.uid].set()          # 按门铃

# wait_for_ack(uid)：住户
while True:
    await event.wait()                 # ① 睡觉等门铃
    event.clear()                      # ② 门铃复位
    pending = self.ack_map[uid]        # ③ 取走全部信，换空信箱
    self.ack_map[uid] = []
    ack = None
    for ack in pending:
        yield ack                      # ④ 一封一封交出去（异步生成器）
    if ack and ack.finished:           # ⑤ 最后一封是 finished 就结束
        break
del self.ack_map[uid]                  # 退租
del self.event_map[uid]
  • 信箱为什么是 list：住户被叫醒前，邮递员可能已经又送来好几封。
  • 为什么只看最后一封的 finished：finished=True 总是最后一条消息。ack = None 防止信箱为空时变量不存在。
  • 为什么这样设计：只有一个读者，不会抢消息；每个请求只在自己的门铃上睡，上千并发也只是上千个门铃。

03为什么 wait 之后马上 clear

一句话Event 只是一盏「有新信」的灯，不装消息。消息在 ack_map 里，关灯不会丢东西。

set() 灯亮，clear() 灯灭，wait() 灯亮立刻返回、灯灭就睡。不 clear 的话，下一轮 wait() 会立刻返回，去看空信箱，再立刻返回……变成空转。

为什么先 clear 再取信

✅ 先关灯再取信：
   1. 关灯   2. 取信  ← 新信到达，灯又亮   3. 下一轮 wait() 立刻返回，取到新信

❌ 先取信再关灯：
   1. 取信  ← 新信到达，灯亮   2. 关灯（把新信的通知也关了）
   3. 下一轮 wait() 睡着，新信躺在信箱没人管

在 asyncio 里两个 await 之间的代码不会被打断，所以这段代码里竞争其实不会发生。但换成 threading.Event 就会真的出 bug，「先清标志、再读数据」是标准写法。

04为什么要 wait for event

一句话没消息时让出控制权睡觉，消息一到就被叫醒。不占 CPU，也没有额外延迟。
做法没消息时消息到达后多久处理
一直查信箱（循环里没有 await）霸占线程，listen() 永远轮不到，整个服务冻结—
每隔一段时间 await asyncio.sleep() 查一次定期醒来白查；1000 请求 × 1ms 间隔 = 每秒 100 万次空查最多一个间隔
await event.wait()完全睡着，0 CPU下一次调度就轮到

05唤醒链：set() 是怎么叫醒协程的

一句话靠 Future（空白回执）、就绪队列和事件循环。set() 填好回执，等待者被放回就绪队列，等当前协程交出控制权后接着跑。
# CPython asyncio.Event 的核心逻辑（简化）
class Event:
    def __init__(self):
        self._waiters = deque()
        self._value = False

    async def wait(self):
        if self._value:
            return True
        fut = loop.create_future()     # 一张空白回执
        self._waiters.append(fut)      # 登记：我在等
        await fut                      # 挂起，直到回执被填上
        return True

    def set(self):
        self._value = True
        for fut in self._waiters:
            fut.set_result(True)       # 填好每张回执
  • await fut 时：协程暂停，保存现场；Task 在 fut 上挂回调「填好时把我放回就绪队列」；Task 离开就绪队列，不占 CPU。
  • set() 时：不会直接切过去，只是把等待者放回就绪队列。listen() 继续跑到下一个 await，事件循环才运行等待者。通常是微秒级。
  • 谁叫醒 listen()：操作系统。事件循环没事干时调用 selector.select()（macOS 是 kqueue，Linux 是 epoll），让线程睡着，直到某个 socket 有数据。
detokenizer 发消息
  → 操作系统：ZMQ 通道有数据 → 叫醒事件循环
  → 事件循环：listen() 放回就绪队列，运行它
  → listen()：放进 ack_map[uid]，event.set()
  → set()：填好 Future → 等待者 Task 放回就绪队列
  → listen() 回到 await recv.get()，交出控制权
  → 事件循环：运行等待者，wait_for_ack 从 await event.wait() 的下一行继续

整条链上没有任何轮询，每一步都是「有事才被叫醒」。

06async 基础

一句话一个线程，谁在等就先放一边去处理别人。适合大部分时间在等待的工作，不适合纯计算。
比喻同步 = 每桌一个专属服务员，客人看菜单时干站着；async = 一个服务员管全场，这桌在看菜单就先去下一桌，谁举手再回来。
import asyncio

async def fetch(name, seconds):      # async def：可以暂停的函数（协程）
    print(f"{name} 开始")
    await asyncio.sleep(seconds)     # await：暂停，让别人先跑
    print(f"{name} 完成")
    return name

async def main():
    results = await asyncio.gather(  # 同时启动，一起等
        fetch("A", 2), fetch("B", 1), fetch("C", 3))
    print(results)

asyncio.run(main())                  # 总共约 3 秒，不是 6 秒
                                     # 把 asyncio.sleep 换成 time.sleep 试试
  • 调用 async def 函数不会执行它：fetch("A", 2) 只是创建协程对象，await fetch("A", 2) 才执行。
  • 传染性：await 只能写在 async def 里，一路往上传到 asyncio.run()。
  • 并发 ≠ 并行：始终只有一个线程，同一时刻只有一段代码在跑。
  • async def + yield = 异步生成器：来一条交一条，用 async for 消费。流式输出就是这样一个字一个字蹦出来的。
最大的坑：在 async 里做阻塞的事 time.sleep(3) 或一段重 CPU 计算不会交出控制权，整个线程上所有任务都卡住。 这就是 tokenizer 是独立进程的原因：分词是纯 CPU 计算，放在 API server 的 async 代码里，分词期间所有用户的流式输出都会卡。拆出去之后，API server 只负责发消息、等结果。
场景适合 async原因
Web 服务器、大量并发连接✅大部分时间在等网络
调用外部 API、爬虫✅大部分时间在等响应
分词、图像处理、数值计算❌CPU 一直在算，没有可切换的空隙
GPU 推理主循环❌同上，而且只有一件事要做

mini-sglang 里两种都有：API server 用 FastAPI + asyncio，同时管上千个等 token 的连接；Scheduler 是普通同步的 while True，一心驱动 GPU，它的并发手段是 CUDA stream，不是 async。用不用 async，看这个进程的时间主要花在等待上还是计算上。
