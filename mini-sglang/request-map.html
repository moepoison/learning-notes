心脏

Scheduler 的一次循环（overlap 模式）

第 5 步其实是在一个死循环里反复发生的。默认开启 overlap scheduling：GPU 跑第 N 个 batch 的同时，CPU 处理第 N-1 个 batch 的结果。所以 _process_last_data 处理的是上一轮的输出，这一点很容易读错。

调度策略：prefill 优先

  • _schedule_next_batch：先问 PrefillManager 要 batch，拿不到再问 DecodeManager。一个 batch 要么全是 prefill，要么全是 decode。
  • prefill 受 max_extend_tokens 预算约束，长 prompt 被切成 ChunkedReq 分几轮做完（chunked prefill）。
  • 准入时先 match_req 查 radix 树，命中的前缀直接复用 KV，只算 extend_len 部分。

Req 的两个指针

  • cached_len：KV 已经写进显存的长度。
  • device_len：当前 token 总长度。两者之差就是本轮要算的 extend_len。
  • 每次 forward 后 complete_one()：cached_len = device_len; device_len += 1。prefill 和 decode 用的是同一套逻辑，decode 就是 extend_len = 1 的 prefill。

四种消息

消息方向携带内容定义
TokenizeMsgAPI → Tokenizeruid、原始 text 或 messages、SamplingParamsmessage/tokenizer.py
UserMsgTokenizer → Scheduler 0uid、input_ids（CPU tensor）、SamplingParamsmessage/backend.py
DetokenizeMsgScheduler 0 → Detokenizeruid、next_token（一个 int）、finishedmessage/tokenizer.py
UserReplyDetokenizer → APIuid、incremental_output（新增的文字）、finishedmessage/frontend.py

每种消息都有对应的 Batch*Msg 包装：一次循环里攒到多条就打包发送，只有一条时直接发原始消息。另外还有 AbortMsg（客户端断开时沿同一条路取消请求）和 ExitMsg。
