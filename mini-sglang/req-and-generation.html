从 Req 到下一个 token

跟着一个请求走完一生：它的状态怎么用两个数字表示，结束时释放了什么，DecodeManager 怎么接手它；再往下钻一层，看模型到底是怎么生成每一个 token 的，以及 Llama 是怎么接进 mini-sglang 的。

Req 的两个指针→请求结束→DecodeManager→模型怎么回答→token 在哪生成→Llama 怎么接进来

01Req：用两个数字记住「算到哪了」

一句话cached_len 是已经算过、KV 存进显存的 token 数；device_len 是目前一共有多少 token。两者之差就是这一轮要算几个。
字段意思会变吗
cached_len已有 KV 缓存的 token 数每轮更新
device_len现在一共有多少 token（prompt + 已生成）每轮 +1
max_device_len最多能有多少 = prompt 长度 + max_tokens固定
extend_lendevice_len − cached_len，这一轮送进模型几个派生
remain_lenmax_device_len − device_len，还剩几个空位派生
can_decoderemain_len > 0，还能不能再生成派生

每次 forward 后两个函数依次执行：

def complete_one(self):             # engine/engine.py forward_batch 里调用
    self.cached_len = self.device_len   # 这一轮送进去的都有缓存了（先执行！）
    self.device_len += 1                # 模型新生成了 1 个 token

def append_host(self, next_token):  # scheduler.py _process_last_data 里调用
    self.input_ids = torch.cat([self.input_ids, next_token])

练习：prompt 10 个 token，max_tokens=3，前缀缓存未命中

第 1 次 forward 后10111112Trueprefill

  • max_tokens=3 正好对应 3 次 forward：1 次 prefill + 2 次 decode。prefill 读完 prompt 的同时也生成了第 1 个输出 token，占用一个名额。
  • decode 就是 extend_len = 1 的 prefill。代码里两者走同一套逻辑。prefill 一次算 10 个，所以首字延迟高；decode 每次只算 1 个，所以之后很快。
  • 第 3 次生成的 token 仍然有效，会发给用户。can_decode=False 只表示不能再继续生成。
我踩过的坑把 device_len 和 max_tokens 搞混：device_len 是现在有多少，max_device_len 才和上限有关。complete_one 的第一行执行时 device_len 还没 +1，所以 prefill 后 cached_len 是 10 不是 0。

02请求结束时发生什么

一句话归还座位（table slot），把 KV 交给前缀缓存保留着，留给以后开头相同的请求复用，而不是直接丢掉。
# scheduler.py  _process_last_data
finished = not req.can_decode
if not req.sampling_params.ignore_eos:
    finished |= next_token == self.eos_token_id      # 或者采到了结束符
reply.append(DetokenizeMsg(uid=req.uid, next_token=next_token, finished=finished))
if finished and req not in self.finished_reqs:
    self.decode_manager.remove_req(req)
    self._free_req_resources(req)

def _free_req_resources(self, req):
    self.table_manager.free(req.table_idx)              # ① 归还座位
    self.cache_manager.cache_req(req, finished=True)    # ② KV 插进 radix 树
  • finished=True 一路传回去：detokenizer 解码最后一个 token → API server 的 wait_for_ack 退出循环、删掉信箱和门铃 → 流式请求发 data: [DONE]。
  • KV 不是丢掉：函数名是 cache_req。KV 进入 radix 树，显存不够时才淘汰；只有放不进树的零头会立刻释放。这就是 RadixAttention。
  • 隐藏细节：结束时 cached_len = 12 不是 13。最后生成的 token 从没被送进模型，没有 KV。
  • 和 pin_memory 无关：锁页内存是每个 batch 临时开的拷贝缓冲区，跟请求的生命周期没关系。

table_idx：请求的座位号

engine/engine.py:69
page_table = zeros((max_running_req + 1, max_seq_len))

                 位置 0      位置 1      位置 2   ...
table_idx = 0  [ KV 在哪  | KV 在哪  | ...        ]   ← 请求 A 占这一行
table_idx = 1  [ KV 在哪  | KV 在哪  | ...        ]   ← 请求 B
table_idx = 2  [ （空闲）                         ]
  • table_idx 是行号；行里每一格才是那个 token 的 KV 在显存里的位置。
  • token_pool 形状相同、行号相同，存的是 token id。
  • table.py 只有 21 行：_free_slots 是空座位列表，allocate() 发座位，free() 收回。座位总数 = max_running_req，也就限制了最多同时跑几个请求。
比喻：餐厅桌号请求进来分一张桌（table_idx），桌上的单子记着每道菜放在仓库哪个货架（page_table 那一行）。吃完桌子收回，但做好的菜（KV）先留在仓库里，说不定下一位点的一样。

03DecodeManager（读到一半）

一句话手里拿着一个 Req 的集合 running_reqs，也就是所有处在 decode 阶段的请求，每轮把它们打包成一个 decode batch。
  • running_reqs 装的是 Req 对象，不是消息。UserMsg 在 scheduler 收到时就转成请求了。
  • prefill 做完之后，请求就进入 decode 阶段。第一个输出 token 是 prefill 生成的，不是 decode。
  • @dataclass(eq=False) 让每个 Req 只和自己相等，所以能放进 set。
self.running_reqs = {req for req in self.running_reqs.union(reqs) if req.can_decode}

04模型是怎么「回答」的

一句话模型只会猜下一个字。回答就是让它一个字一个字接着写，每次猜出的字接到末尾，作为下一次的输入（自回归）。

你的问题会先被套上对话模板，变成 <用户>中国的首都是哪？<助手>。模型看到 <助手>，就以助手的身份续写。它不是在回答，而是在续写一段对话。

轮次送进模型的模型看到的全部内容猜出的下一个字
1 · prefill整个 prompt（10 个 token）<用户>中国的首都是哪？<助手>北
2 · decode只有「北」…<助手>北京
3 · decode只有「京」…<助手>北京。
4 · decode只有「。」…<助手>北京。EOS → 停
  • 为什么 decode 只送 1 个字也能看到前文：前面字的 KV（笔记）已经存在显存里，只需给新字做笔记，再翻旧笔记。
  • 你看到的只有「北京。」：detokenizer 只把新生成的 token 转成文字（incremental_output），一点点流回来。

input_ids ─▶ [Transformer 层] ─▶ [LM head：prefill 只取最后位置] ─▶ logits（词表打分）
                                                                      │
                                                              [Sampler：挑一个]
                                                                      │
                                                     next_token ─▶ append_host ─▶ detokenizer
站位置做什么
1models/llama.py:79跑完所有层，lm_head 把结果变成词表上每个词的分数（logits）
2layers/embedding.py ParallelLMHead.forwardprefill 时用 get_last_indices 只留每个请求最后一个位置。前面位置的预测没用，不浪费算力打分
3engine/sample.py:71greedy 直接 argmax；否则按 temperature / top_k / top_p 用 FlashInfer 随机采样
4engine/engine.py:191forward_batch 串起前三站，complete_one()，结果异步拷回 CPU

prefill 送进 10 个 token 却只出 1 个新 token，原因就在第 2 站：只有最后一个位置代表「prompt 之后的下一个字」。

06Llama 是怎么接进 mini-sglang 的

一句话mini-sglang 没用 HuggingFace 的模型代码，而是自己重写了 Llama。只从 HF 拿 config.json、tokenizer 和 .safetensors 权重。

全局 Context

self.model.forward() 不传参数，模型自己去 get_global_ctx() 取 batch、positions、attn_backend、kv_cache。注意力层要的东西太多，全当参数传会让每层签名又长又乱；放进全局 Context，模型代码就和普通 Llama 实现差不多干净。代价是光看签名看不出依赖。
