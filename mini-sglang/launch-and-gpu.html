启动与 GPU 分工

从 launch.py 读起：几张卡就开几个 scheduler 进程，每个进程靠 rank 知道自己是谁。然后退一步看清楚 CPU 和 GPU 怎么分工：哪些东西启动时就放上 GPU 再也不动，每一轮来回搬的又是什么，overlap 到底在和谁重叠。

world_size 与 rank→replace 与 frozen→scheduler 进程→代码在 CPU，计算在 GPU→什么在 GPU 上→overlap 重叠的是谁→CUDA Graph

01world_size 与 rank

一句话world_size 是你让它用几张卡（--tp-size），不是机器上有几张；rank 是每个进程的编号，告诉它「我是第几张卡」。
# args.py:87, 262
"--tensor-parallel-size", "--tp-size"
kwargs["tp_info"] = DistributedInfo(0, kwargs["tensor_parallel_size"])

# launch.py
world_size = server_args.tp_info.size
for i in range(world_size):
    new_args = replace(server_args, tp_info=DistributedInfo(i, world_size))
    mp.Process(target=_run_scheduler, args=(new_args, ack_queue), name=f"minisgl-TP{i}-scheduler").start()
  • 机器有 8 张卡、写 --tp-size 2，就只用 2 张；不写默认 1。
  • 名字来自分布式训练：参与计算的所有进程组成一个「世界」。mini-sglang 里一张卡 = 一个 scheduler 进程。

02replace 与 frozen

一句话dataclasses.replace 复制一份 dataclass，只改指定字段。这里就是给每个进程发一份写着自己编号的参数。
模型路径、端口等tp_info
server_args（原件）一样(0, 2)
给 rank 0 的副本一样(0, 2)
给 rank 1 的副本一样(1, 2)

为什么不直接改原件：ServerArgs、DistributedInfo、EngineConfig 都是 @dataclass(frozen=True)，造出来就不能改，server_args.tp_info = ... 会报 FrozenInstanceError。配置要传给好几个进程、在代码里到处传，冻住以后每个进程拿到的是一份定死的、属于自己的配置，不会被哪里偷偷改掉。

03每张卡一个 scheduler 进程

一句话不是「每个进程里都有 scheduler」，而是这个循环专门为每张卡开一个进程，这个进程的活就是跑 scheduler。tokenizer、detokenizer 是另外的进程，跑的是 tokenize_worker。
# launch.py:16  _run_scheduler，每个 scheduler 进程进来后做的事
scheduler = Scheduler(args)          # 1. 建 scheduler（里面建 Engine，模型和 KV cache 放上自己的卡）
scheduler.sync_all_ranks()           # 2. 等所有卡都准备好
if args.tp_info.is_primary():
    ack_queue.put("Scheduler is ready")   # 3. 只有 rank 0 报到
scheduler.run_forever()              # 4. 进入主循环，永远跑下去
  • 进程 ≠ task。async 笔记里的 task 是同一个进程里轮流跑的协程；这里是真的另起一个 Python 解释器，各自占内存、各自用一张卡。

04代码在 CPU，计算在 GPU

一句话所有 Python 代码都在 CPU 上执行。区别只在于某一行有没有给 GPU 发命令。
a = torch.ones(1000, device="cuda")   # a 的数据在显存里
b = a + 1                             # CPU 执行这行 = 给 GPU 发一条「每个数加 1」的命令
x = 5 + 1                             # 纯 CPU，GPU 不知道
比喻遥控器和电视：你按遥控器（CPU 跑 Python），电视换台（GPU 计算）。遥控器本身不在电视里。run_forever 就是一直在按遥控器的那只手。
run_forever 里的代码谁在做
if ENV.DISABLE_OVERLAP_SCHEDULING、while True纯 CPU
engine.stream.wait_stream(self.stream)CPU 给 GPU 发「engine 队列先等 scheduler 队列」
overlap_loop 里收消息、排队纯 CPU
overlap_loop → _forward → engine.forward_batch → model.forwardCPU 发大量命令，GPU 算
  • @torch.inference_mode() 和 GPU 无关：只是告诉 PyTorch 不记计算图（训练才需要），省显存、更快。见 Overlap 笔记第 01 节。
  • scheduler.py:53-55 三行只是在卡上开命令队列（scheduler stream、engine stream），不搬数据。
我说的收消息和排队是 CPU，forward 是 GPU。

05什么在 GPU 上，什么时候放上去

一句话大头（权重、KV cache、token_pool）在启动时就放上 GPU，之后不动；每一轮只来回搬一点点。因为 CPU↔GPU 的通道（PCIe）比显存慢很多，能不搬就不搬。

└─ Scheduler(args)                  (scheduler.py:46)

   │  ├─ 选卡 cuda:{rank}           (engine.py:35)
   │  ├─ ① 权重                     (engine.py:52)
   │  ├─ ② KV cache                 (engine.py:57)
   │  └─ page_table                 (engine.py:69)
   └─ ③ token_pool                  (scheduler.py:71 → table.py:11)
东西怎么上 GPU启动时有内容吗

KV cachecreate_kvcache_pool 在显存里划一大块地空的，请求来了才写
token_pooltorch.zeros_like(page_table)，跟着 page_table 在 GPU 上全 0；prefill 时写入 prompt，decode 时 GPU 自己追加

  • 新请求的 prompt token id 要在 prefill 时从 CPU 上传一次，之后的 token 都是 GPU 自己产、自己存。
我说的所以是 CPU 给 GPU，GPU 算完再拿回来？（大方向对，但大头一直留在 GPU 上不动，来回的只是索引和每个请求一个 token。）

06overlap 重叠的是 CPU 和 GPU

一句话GPU 算第 N 轮的同时，CPU 处理第 N−1 轮的结果、安排第 N+1 轮，谁都不干等。
不 overlap（normal_loop）：
CPU: [排第1轮] ...等...  [处理第1轮][排第2轮] ...等...  [处理第2轮]
GPU:           [算第1轮]                     [算第2轮]
                        ↑ GPU 闲着                     ↑ GPU 闲着

overlap（overlap_loop）：
CPU: [排第1轮][排第2轮 + 处理第1轮][排第3轮 + 处理第2轮]
GPU:          [算第1轮]           [算第2轮]           [算第3轮]
data = None
while True:
    data = self.overlap_loop(data)   # 传进去的是「上一轮」的结果，拖后一轮处理

为什么 token 留在 GPU 上很关键：第 N+1 轮的输入就是第 N 轮的输出。如果 token 必须先回 CPU 再送回 GPU，CPU 就得等第 N 轮算完才能安排第 N+1 轮，又变回「互相等」。

07CUDA Graph：把一千下遥控器录成一个宏按钮

一句话decode 时 GPU 算一条命令可能比 CPU 发这条命令还快，GPU 一直在等命令。CUDA Graph 启动时把 forward 的整串命令录下来，之后每轮 CPU 只发一条「回放」。

和 overlap 的区别

解决的「等」怎么解决
overlapGPU 等 CPU 排队、处理结果CPU 提前一轮干，和 GPU 同时进行
CUDA GraphGPU 等 CPU 在 forward 里一条条发命令（几百上千条）录成一条，发一次

录下来的到底是什么

一张命令清单，不是数据。每条命令记死三样：调哪个函数、数据多大（如 [4, 4096]，4 就是 batch size）、去哪个地址读写。没记死的是地址里装的数字。

比喻固定的菜谱卡：「从 3 号碗取 4 勺料，炒好盛到 7 号盘。」回放时 3 号碗里可以放今天的新菜，但碗的位置和勺数改不了。
# engine/graph.py:152
def replay(self, batch):
    self.buffer.copy_from(batch)              # ① 新数据拷进录制时用的固定显存（换碗里的菜）
    g = self.graph_map[batch.padded_size]     # ② 挑一张录好的图
    self.attn_backend.prepare_for_replay(batch)
    g.replay()                                # ③ 回放
    return self.buffer.logits[: batch.size]   # ④ 只取真实请求的结果

为什么 decode 能用、prefill 不行

  • prefill：prompt 长度可以是 1 到几万之间任意数，「勺数」每次都不一样，不可能每种长度都录一张。
  • decode：每个请求每轮固定送 1 个 token，形状只取决于 batch size。
我踩过的坑一开始以为「因为 prefill 要算 KV」。不对，decode 也要算新 token 的 KV 写进 cache。真正的原因是 prefill 的长度不固定。

batch size 也会变：pad

录好的图：1、2、4、8 ……
真实请求：  A  B  C  D  E                → 5 个，没有 5 号图
pad 之后：  A  B  C  D  E  假 假 假       → 8 个，用 8 号图

# graph.py:166
batch.padded_reqs = batch.reqs + [self.dummy_req] * (padded_size - batch.size)
  • 假请求也会被算，结果被 logits[: batch.size] 扔掉。
  • 假请求必须安全：dummy_req 坐 page_table 多出来的那一行（+ 1 for dummy request），token_pool 初始化成 0 也是为了让它读到合法的 token id。
  • 多算几个假的几乎不花时间，省下的是几百次发命令的等待。
  • 超过最大录制 batch size（cuda_graph_max_bs）就退回普通 model.forward()。CUDA Graph 主要救的是小 batch 的 decode。
比喻餐厅只有 2、4、8 人桌，5 个人坐 8 人桌，空 3 个座位，总比现搭一张桌子快。
